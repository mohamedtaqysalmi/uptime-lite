An uptime monitor that waits for a real outage before it alerts.

Most small-site monitors either alert on one dropped request or need a hosted account. I wrote this to run on my own machine: it checks HTTP and TCP targets, opens an incident only after several failures in a row, keeps history in SQLite and writes the public status page as one plain HTML file.

Debounce demo

A check goes down after N failures in a row and comes back after M passes in a row. Set N and M, then send results one at a time or replay a pattern. A result of the opposite kind resets the streak, which is why a flapping check stays quiet.

This is a JavaScript port of the Python state machine. Both run the same cases from debounce-cases.json in the test suite, so they cannot disagree without a test failing.

      • works Debounced incidents. The streak is stored in SQLite, so a restart continues it.
      • works Static status page, generated from the database.

      Quickstart

      git clone https://github.com/mohamedtaqysalmi/uptime-lite
cd uptime-lite
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e .
cp examples/config.example.yaml config.yaml
uptime-lite check -c config.yaml --no-alerts
uptime-lite status-page -c config.yaml -o status

      The example config points at example.com and documentation addresses, so some checks will fail. Edit the targets to something you own.

      How it works

      Every result is stored, then passed to a pure function that returns the new state and, when a threshold is crossed, an opened or resolved event. Only those events trigger alerts. 

      config.yaml
    │
    ▼
uptime-lite check ──► SQLite: results, state, incidents
    │                      │
    │                      └──► uptime-lite status-page ──► index.html
    │
    └──► Telegram / webhook, only when an incident opens or resolves

      How I built it

      The debounce is a pure function

      It takes the old state, the result and a timestamp, and returns the new state. No clock, no database, so the tests drive it with exact sequences and the demo above could be ported and checked against the same cases.

      One transaction per result

      The result, the new state and the incident row are written together. A crash between them cannot leave an open incident with no state, or the reverse.

      Tokens only from the environment

      The config loader rejects a bot token written in YAML, so a config file is safe to commit. The Telegram token is read from TELEGRAM_BOT_TOKEN when an alert is sent.

      A file, not a web app, for the public page

      The status page is generated HTML with no scripts. It can sit on any static host, and the monitor never has to be reachable from the internet.

      Limits and roadmap

      • One node, one SQLite file. It is not a multi-region monitor.
      • Results are never pruned yet, so the database grows without bound.
      • The example status page above is a snapshot, not a feed from a running monitor.

      The plan is in the open issues. To contribute, start with CONTRIBUTING.md.
