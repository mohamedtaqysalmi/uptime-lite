uptime-lite

I built this because most uptime tools I tried either flapped on one failed probe or needed a hosted account I did not want for small client sites. This one keeps history in SQLite, opens incidents only after N failures in a row, and writes a public status page as plain HTML.

What problem it solves

You want a private probe that can alert you on Telegram and still publish a public page without running a second web app. Debounce stops a single timeout from paging you at 3 a.m.

  • HTTP and TCP checks from YAML, validated before anything runs.
  • Incident state machine with failure and recovery thresholds.
  • Telegram bot and generic webhook alerts; tokens stay in env vars.
  • Static status HTML you can host anywhere, including GitHub Pages.

Quickstart

python -m venv .venv
.venv\Scripts\activate
pip install -e ".[dev]"
copy examples\config.example.yaml config.yaml
uptime-lite check -c config.yaml -d uptime.db --no-alerts
uptime-lite status-page -c config.yaml -d uptime.db -o status

How it works

Each check result is stored, then fed into a pure evaluate() call. Only when a streak crosses the threshold does an incident open or resolve, and only then do alerts fire. 

config.yaml
    │
    ▼
uptime-lite check ──► SQLite (results, state, incidents)
    │                        │
    │                        ├──► Telegram / webhook (on transition)
    │                        │
    └── status-page ─────────┘──► index.html

Honest limits

  • No long-running scheduler yet; use cron/Task Scheduler with check.
  • Single-node SQLite. Fine for tens of checks; not a multi-region mesh.
  • Resource numbers in the docs use fake transports; real RTT is yours to measure.
  • Pages demo is a static snapshot, not a live feed from a running monitor.

How I built it

  1. Debounce as a pure function so tests can drive a fake clock.
  2. One SQLite transaction per result so state and incidents cannot diverge.
  3. Reject bot tokens in YAML; read them from the environment at send time.
  4. Generate HTML instead of serving a live API for the public page.
  5. Ship one-shot CLI first; interval loop is tracked for later.

Longer notes live in docs/architecture.md.

Tests and CI

Coverage gate is 85% branch coverage. The incident machine is the focus of the suite; alerts use injectable HTTP posters so tests never call Telegram.
